# Connect-flow lifecycle + workspace-консолидация — Design

**Дата:** 2026-05-17
**Подпроект:** connect-flow lifecycle fix (объединённая задача «бот удалён» + «1 Pulse = 3 ws»)
**Версия:** V1.17.0h · ветка `feat/V1.17.0h-connect-flow-lifecycle`
**Флаг:** `CONNECT_FLOW_V2` (дефолт **OFF** = байт-в-байт)
**Процесс:** брейншторм проведён автономно (Илья дал «без подтверждения
продолжай»); решения зафиксированы в §Assumptions вместо интерактивных
вопросов.

---

## 1. Проблема (две, один корень)

**#1 «Бот удалён»:** админ удаляет бота из чата → на сайте сообщество
висит как рабочее (нет статуса «отключён»); при повторном добавлении
роль теряется (`add_bot_chat role=None`) → бот молчит (H оживает только
при `role='main'`).

**#2 «1 Pulse = 3 workspace»:** connect-flow создаёт новый workspace на
каждый чат → один логический Pulse Ильи размазан по ws1/ws5/ws6.

Оба — про lifecycle одной подсистемы (connect-flow / bot membership).

## 2. Ground truth (по коду + проду 17.05)

**Дубль-хендлер MY_CHAT_MEMBER (корень #1):**
- `bot.py:734` → `bot_membership.on_bot_added_to_chat` (group 0,
  зарегистрирован ПЕРВЫМ) — на `left/kicked` зовёт `remove_bot_chat`
  (`db_workspaces.py:213` = **hard `DELETE FROM bot_chats`**).
- `bot.py:750` → `bot_chat_tracker.handle_my_chat_member` (group 0,
  ВТОРОЙ) — на уход зовёт `mark_bot_chat_removed` (**мягкая пометка
  `removed_at`**).
- PTB в одной группе запускает ТОЛЬКО первый matching-хендлер →
  `handle_my_chat_member` для `my_chat_member` **мёртв**. Срабатывает
  hard-delete; мягкий путь существует, но недостижим.

**Soft-disconnect инфраструктура УЖЕ есть (но мёртвая):**
- `db_press_release.py:68` `bot_chats` имеет `removed_at TIMESTAMP`,
  `last_seen_at`. `upsert_bot_chat` при ре-добавлении ставит
  `removed_at=NULL` (восстановление!). `mark_bot_chat_removed` ставит
  `removed_at=now`, **роль не трогает** (роль сохраняется → restore).
- Т.е. возможность восстановления роли уже заложена — нужно лишь
  убрать затенение и научить connect-flow/H уважать `removed_at`.

**Прод-данные (probe 17.05) — консолидация тривиально безопасна:**

| ws | name | owner | pulse_themed | chat / role | tenant-данные |
|----|------|-------|--------------|-------------|---------------|
| 1 | Pulse Москва | Илья 7536752126 | **1** | -1003900924578 / main | economy 68, stats 7348, topics 34848, triggers 9 |
| 5 | Журнал MAIN | Илья | 0 | -1003846550693 / journal | **0 (пусто)** |
| 6 | MAIN_ADMIN_CHat | Илья | 0 | -1003926472546 / admin | **0 (пусто)** |
| 7 | Тест коннект | Кирилл 8376708692 | 0 | — (0 чатов) | **0** — живой кейс бага #1 |

ws5/ws6 — пустые оболочки (workspace + 1 member + 1 bot_chats строка с
уже правильной ролью). Консолидация = перепривязать 2 bot_chats на ws1
+ удалить пустые ws5/ws6. Ноль потерь. Бонус: чинит H4-долг
(`resolve_thread` ws1 'applications' указывал в admin-чат ws6 — после
консолидации admin-чат становится ws1-овским).

## 3. Подходы (рассмотрено 3)

**A. Soft-disconnect через существующий `removed_at` + унификация
хендлера (РЕКОМЕНДУЮ).** Убрать затенение: один MY_CHAT_MEMBER-хендлер;
уход → `removed_at=now` (роль/ws сохраняются); ре-добавление →
`removed_at=NULL`, роль восстановлена → бот оживает. connect-flow и H
учитывают `removed_at`. Сайт-бейдж из этого же признака.
*Плюс:* переиспользуем готовую инфру, минимум нового кода, обратимо
флагом. *Минус:* надо аккуратно с двумя «вью» схемы bot_chats.

**B. Новая колонка `disconnected_at` + новый слой.** Дублирует то, что
уже есть (`removed_at`). Больше кода, выше риск рассинхрона двух
механизмов. Отверг.

**C. Только сайт-бейдж из `chats_count==0`, hard-delete оставить.**
Дёшево, но НЕ решает потерю роли при реконнекте (#1 половина) и никак
не трогает #2. Недостаточно.

→ **A.**

## 4. Дизайн (компоненты)

Всё за флагом `CONNECT_FLOW_V2` (OFF = байт-в-байт: hard-delete и
старый connect-flow без изменений).

**C1 — Минимальная правка точки удаления (без трогания регистрации).**
Регистрацию хендлеров (`bot.py:734/750`) НЕ меняем — это снижает риск
и сохраняет байт-в-байт при OFF. `on_bot_added_to_chat` и так
единственный, кто реально обрабатывает `my_chat_member` (второй
затенён PTB). Меняем ТОЛЬКО ветку `left/kicked` внутри
`on_bot_added_to_chat`: при `CONNECT_FLOW_V2` ON → мягкая пометка
`removed_at` вместо `remove_bot_chat` (hard DELETE); при OFF →
прежний `remove_bot_chat` строка-в-строку. Затенённый
`bot_chat_tracker.handle_my_chat_member` остаётся как есть (его
поведение не меняется ни при ON, ни при OFF) — рефактор дубля
вынесен в §8 техдолг.

**C2 — Идемпотентная миграция `removed_at`.**
`ALTER TABLE bot_chats ADD COLUMN removed_at TIMESTAMP` если колонки
нет (PRAGMA-проверка, как остальные миграции проекта). Standalone +
вызывается при старте идемпотентно. Безопасно и для OFF.

**C3 — Мягкий disconnect + restore роли.**
- Уход бота → `removed_at=CURRENT_TIMESTAMP`, `workspace_id` и `role`
  НЕ трогаются.
- Ре-добавление → если есть строка с `removed_at IS NOT NULL` для
  этого chat_id: `removed_at=NULL`, роль сохранена → бот сразу
  работает (H видит `role`), сообщение «переподключён, роль
  «<role>» восстановлена». Меню «куда подключить» НЕ показывается.

**C4 — connect-flow prevention (#2).**
Когда бота добавляет владелец, у которого уже есть workspace(ы):
по умолчанию предлагать **привязать чат ролью к существующему
сообществу** (выбор роли main/admin/journal на кнопках), «🆕 Создать
новое сообщество» — вторичная опция. Привязка ставит выбранную роль,
НЕ `role=None`. Это устраняет порождение лишних ws на будущее.

**C5 — `get_workspace_by_chat` / H-резолв уважают `removed_at`.**
Активным считается чат с `removed_at IS NULL`. soft-removed чат для
рантайма «не привязан» (бот не обслуживает), но строка хранит ws+role
для восстановления C3. Точечно: добавить фильтр/хелпер, не ломая
текущие вызовы при OFF.

**C6 — Сайт-бейдж «бот не в чате» (Piece D, отдельный деплой сайта).**
API уже отдаёт `chats_count` (`get_workspaces_for_user`) и список
чатов с ролями (`get_workspace_details`). Добавить в выдачу признак
«нет активных чатов / есть removed». Admin_SITE (React) показывает
🔴-бейдж на карточке/в свитчере. Read-only индикатор, тумблер не
нужен; деплой сайта отдельным юнитом (тег `[Site]`,
локальный билд → деплой).

**C7 — Одноразовая консолидация ws5/ws6→ws1 (Piece C, прод-данные).**
`scripts/consolidate_workspaces.py --from 5,6 --into 1` :
1. backup БД (копия с таймстампом);
2. dry-run по умолчанию — печатает план (перепривязка 2 bot_chats,
   удаление ws5/ws6 + их workspace_members), считает что осиротеет
   (по проду — ничего);
3. `--apply` — выполняет в транзакции; роли bot_chats сохраняются
   (journal/admin уже стоят);
4. защита: отказ если у переносимого ws есть НЕпустые tenant-таблицы
   (economy/stats/...) — тогда требует ручного решения;
5. обратимо из backup; idempotent (повторный запуск = no-op).
Выполняет Илья по возвращении (живой прод, Илья/Кирилл онлайн).

## 5. Поток данных

```
[admin удаляет бота] → my_chat_member(left/kicked)
  → единый хендлер (CONNECT_FLOW_V2 ON)
  → bot_chats.removed_at = now   (ws_id, role СОХРАНЕНЫ)
  → сайт: ws показывает 🔴 «бот не в чате»

[владелец снова добавляет бота] → my_chat_member(member/admin)
  → строка с removed_at NOT NULL?
     да → removed_at=NULL, роль восстановлена → бот работает (H)
     нет → connect-flow: привязать ролью к существующему ws
           (C4), либо создать новое (вторично)
```

## 6. Обработка ошибок

- Гонка add/remove событий Telegram: операции идемпотентны
  (upsert/обновление по chat_id), повторное событие не ломает.
- `removed_at` колонки нет на старте → C2 добавит до первого
  использования; при OFF ветка не вызывается.
- Консолидация: любой непустой tenant-данные у source-ws → STOP,
  ручное решение (на проде не наступит, но защита обязательна).
- Двойной хендлер — регистрацию НЕ трогаем ни при ON, ни при OFF
  (C1); рефактор дубля = техдолг §8.

## 7. Тесты (TDD)

- `test_connect_flow_lifecycle.py`: уход → `removed_at` выставлен,
  ws_id/role сохранены; ре-добавление → `removed_at=NULL`, роль та же,
  меню не показано; флаг OFF → старый hard-delete (байт-в-байт, роль
  исчезает как раньше).
- connect-flow C4: владелец c ws → кнопки ролей к существующему ws;
  привязка ставит роль (не None); «создать новое» всё ещё доступно.
- C5: `get_workspace_by_chat` для removed чата → «не активен» при ON;
  при OFF — прежнее поведение.
- `test_consolidate_workspaces.py`: dry-run ничего не меняет; apply
  переносит bot_chats, удаляет пустые ws, роли сохранены; защита
  срабатывает при непустом source; idempotent; round-trip из backup.
- Прогон всего сьюта без регрессов (база 219).

## 8. Вне скоупа

- Слияние НЕпустых workspace с конфликтом tenant-данных (не наступает
  на проде; универсальный merge — отдельная задача при реальном кейсе).
- Полный рефактор двух «вью» bot_chats (db_workspaces vs
  db_press_release) в один модуль — техдолг, отметить, не делать сейчас.
- Биллинг/тарифные эффекты числа workspace.

## 9. Activation plan (путь A, как H/I/g)

push ветки → main → авто-деплой (`deploy.yml`, флаг OFF = байт-в-байт,
рестартит pulsbot+pulsapi) → проверить прод чист → C2-миграция
идемпотентна (применится сама/одноразово) → в `/root/PulsBot/.env`
`CONNECT_FLOW_V2=1` → `systemctl restart pulsbot` → smoke с Ильёй:
удалить бота из тест-чата → ws помечен removed, бот молчит → добавить
обратно → роль восстановлена, бот ожил. **Консолидация (C7) и деплой
сайта (C6) — отдельные явные шаги с Ильёй.** Откат: убрать флаг +
рестарт; БД — миграция `removed_at` аддитивна и безвредна при OFF.

## 10. Assumptions (брейншторм автономный)

1. Используем существующий `removed_at`, НЕ вводим новый
   `disconnected_at` (избегаем дубль-механизма).
2. connect-flow prevention = выбор роли при привязке к
   существующему ws; «создать новое» остаётся вторичной опцией.
3. Консолидация — точечная явная (`--from 5,6 --into 1`), без
   эвристик; защита на непустой source обязательна.
4. Сайт-бейдж — read-only индикатор, без тумблера; деплой сайта
   отдельным юнитом.
5. Флаг `CONNECT_FLOW_V2` дефолт OFF = строго байт-в-байт.
6. Один spec, но реализация фазами: P1 backend lifecycle+флаг+тесты
   (C1-C3,C5), P2 prevention (C4), P3 консолидация-скрипт (C7),
   P4 сайт-бейдж (C6). P3/P4 — отдельные деплой-юниты, выполняются
   с Ильёй.
7. Необратимые/наружные шаги (исполнение C7 на живом проде, публикация
   сайта C6) НЕ выполняются без явного «go» Ильи, несмотря на общую
   автономию — они hard-to-reverse.
